# Создание клиентского репозитория

Эта инструкция описывает полный путь от нового GitHub-репозитория до опубликованного меню.

## 1. Создать пустой публичный репозиторий клиента

Все клиентские репозитории должны быть публичными: это обеспечивает публикацию
GitHub Pages на бесплатном тарифе GitHub.

### Через терминал (GitHub CLI)

Установите [GitHub CLI](https://cli.github.com/) и авторизуйтесь:

```bash
gh auth login
```

Создайте пустой публичный репозиторий:

```bash
gh repo create menu-anna --public
```

Команда создаёт репозиторий без README, `.gitignore` и License. По умолчанию
репозиторий создаётся в вашем личном аккаунте. Чтобы создать его в организации,
укажите владельца в имени: `OWNER/menu-anna`.

### Через сайт GitHub

На GitHub создайте новый **публичный** репозиторий без README, `.gitignore` и License.
Например, `menu-anna`.

## 2. Клонировать шаблон и подключить репозиторий клиента

Клонируйте шаблон, затем измените URL уже созданного `origin`, чтобы он указывал
на пустой клиентский репозиторий. Не переименовывайте `origin` в `upstream`:
Git может перенести настройку отслеживания локальной ветки на `upstream`, и обычный
`git push` тогда отправит клиентские коммиты в общий шаблон.

```bash
git clone https://github.com/Wwwoper/template-menu.git menu-anna
cd menu-anna
git remote set-url origin https://github.com/OWNER/menu-anna.git
git remote add upstream https://github.com/Wwwoper/template-menu.git
```

Замените `OWNER/menu-anna` на владельца и имя созданного репозитория. Настройте
репозиторий так, чтобы push по умолчанию направлялся только в `origin`:

```bash
git config --local remote.pushDefault origin
git config --local push.default simple
```

Проверьте настройки до импорта и первой отправки:

```bash
git remote -v
git config --get remote.pushDefault
git branch -vv
```

Ожидаемый результат: `origin` указывает на `https://github.com/OWNER/menu-anna.git`,
`upstream` — на `https://github.com/Wwwoper/template-menu.git`, а
`remote.pushDefault` выводит `origin`. Если URL перепутаны, исправьте их до продолжения.

До первой отправки локальная ссылка `origin/main` ещё может содержать состояние,
полученное при клонировании шаблона. Это нормально: первая команда
`git push -u origin main` ниже создаст ветку `main` в клиентском репозитории и
настроит её отслеживание.

## 3. Подготовить Excel и создать клиента

Установите зависимости (нужны Python 3.11+ и [uv](https://github.com/astral-sh/uv)):

```bash
uv sync
```

Положите исходную книгу `.xlsx` в папку `input/` и запустите:

```bash
uv run tools/create_client.py
```

Следуйте подсказкам: выберите книгу, введите имя клиента точно как в заголовках Excel, проверьте сводку и подтвердите импорт.

Скрипт инициализирует приложение, создаст JSON-дни в `content/days/`, проверит данные и построит локальный индекс. После успешного импорта исходная книга будет перемещена в `input/archive/`.

**Важно:** `input/` целиком исключена из Git. Не переносите исходные таблицы в другие отслеживаемые каталоги и не добавляйте их в коммиты: они могут содержать персональные данные и учётные сведения.

Если требуется, короткое название приложения можно передать параметром:

```bash
uv run tools/create_client.py --short-name "Анна"
```

## 4. Проверить результат

```bash
uv run tools/validate.py
uv run pytest
node --test tests/js/*.test.mjs
git status --short
```

Проверьте название клиента и содержимое `content/days/`. Исходный XLSX и его архив не должны отображаться в `git status`.

`content/days.json` — генерируемый индекс, он исключён из Git. В репозитории хранятся исходные JSON-файлы из `content/days/`.

## 5. Включить GitHub Pages

До первой отправки изменений откройте в репозитории клиента **Settings → Pages → Build and deployment** и выберите **GitHub Actions** в поле Source.

Это нужно сделать до первого push: тогда первый запуск workflow сразу сможет опубликовать сайт, а не завершится ошибкой из-за невыбранного источника публикации.

## 6. Сохранить и отправить клиентский проект

```bash
git add -A
git commit -m "chore: initialize client menu"
git push -u origin main
```

Если основная ветка шаблона называется не `main`, используйте соответствующее имя ветки.

После push в основную ветку workflow проверит данные, соберёт индекс, запустит тесты и опубликует сайт. Результат и адрес публикации можно проверить в **Actions** и **Settings → Pages**.

## 7. Получать обновления шаблона

Обновления приложения переносите из `upstream` в отдельной ветке. Не заменяйте клиентские JSON-файлы содержимым шаблона.

Подробная процедура описана в [TEMPLATE_UPDATES.md](TEMPLATE_UPDATES.md).
